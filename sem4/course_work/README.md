
# Интеллектуальная система управления «Умный дом» (OSTIS)
**Подсистема автоматизации по расписанию и семантическая база знаний**

Исходный код проекта: [ostis_smart-home](https://github.com/MatsukSket/ostis-smart-home)

Данный раздел проекта посвящен разработке ядра интеллектуальной системы умного дома на базе открытой семантической технологии [OSTIS](https://ostis.net/). В рамках данной работы была спроектирована онтологическая модель умного дома и реализован событийный C++ решатель задач для автоматического управления IoT-устройствами по расписанию.


## Мой вклад в проект

В рамках работы над данным репозиторием мной были спроектированы и реализованы три ключевых компонента системы:
1. **Семантическая база знаний умного дома** (язык SCs).
2. **Агент системного времени** (`ScheduleTickerAgent`, C++).
3. **Агент мониторинга расписаний** (`DeviceScheduleMonitorAgent`, C++).
4. **Комплекс автоматизированных тестов** (Google Test).

Ниже приведено подробное описание каждого из реализованных модулей.


## 1. Разработка семантической базы знаний

База знаний спроектирована в виде направленного графа (sc-памяти) и разделена на логические подмодули для обеспечения масштабируемости. Исходные файлы находятся в директории `knowledge-base/smart-home/`.

### Архитектура базы знаний:
* **Терминологическая онтология (`concepts/`)**: Задает таксономию предметной области. Описаны базовые классы приборов (`concept_smart_socket`, `concept_light_bulb`, `concept_humidity_sensor`), типы локаций (`concept_room`, `kitchen`, `bedroom`) и профили пользователей.
* **Отношения (`relations/`)**: Введены ключевые неролевые (`nrel_location`, `nrel_status`, `nrel_schedule`) и ролевые (`rrel_day`, `rrel_time_on`, `rrel_time_off`) отношения, описывающие семантику связей между узлами.
* **Топология и примеры (`entities/`, `examples/`)**: Содержит фактуальные данные — конкретную планировку помещений и экземпляры умных устройств с заданными параметрами.

**Пример реализованной структуры расписания (SCs):**
```scs
socket_bedroom_1
    => nrel_location: bedroom;
    => nrel_status: concept_device_off;
    => nrel_schedule: schedule_socket_bedroom_1 
    (*
        -> rrel_day: monday;;
        -> rrel_time_on:;;
        -> rrel_time_off:;;
    *);;
```

*Данная структура позволяет системе "понимать", что устройство должно быть включено в понедельник в 07:00 и выключено в 09:00.*


## 2. Разработка интеллектуальных SC-агентов (C++)

Процедурная логика автоматизации реализована с использованием `sc-memory` API (стандарт C++17). Агенты работают асинхронно, опираясь на событийно-ориентированную модель ядра `sc-machine`. Исходный код агентов расположен в `problem-solver/cxx/smart-home-module/agents/schedule-agent/`.

###  ScheduleTickerAgent (Агент времени)

Выступает в роли *Producer* в архитектуре умного дома.

* **Логика работы:** Агент регулярно инициируется системным таймером. При каждом срабатывании он генерирует в графовой памяти узлы, отражающие текущее физическое время (sc-link со строкой, например `[07:00]`) и текущий день недели.
* **Управление памятью:** Перед созданием новой временной метки агент использует `ScTemplate` для поиска и безопасного удаления (через `context->EraseElement`) устаревшей метки, предотвращая переполнение sc-памяти.

### DeviceScheduleMonitorAgent (Монитор расписаний)

Выступает в роли *Consumer* и главного решателя задач автоматизации по времени.

* **Триггер:** Агент подписывается на событие появления новой метки времени в базе знаний (генерируемой `ScheduleTickerAgent`).
* **Семантический поиск:** Получив управление, агент формирует сложный `ScTemplate`, который ищет изоморфные подграфы в базе знаний. Он сопоставляет текущее время и день недели с ролевыми атрибутами `rrel_time_on` / `rrel_time_off` узлов `nrel_schedule` всех IoT-устройств.
* **Трансформация графа:** При нахождении совпадения, агент находит текущую дугу статуса устройства (`nrel_status`), удаляет её и динамически генерирует новую дугу к узлу `concept_device_on` (включение) или `concept_device_off` (отключение).

## 3. Покрытие тестами (Unit & Integration Testing)

Для проверки корректности работы агентов и целостности графа памяти был написан комплекс тестов с использованием фреймворка **Google Test** (файл `TestSchudleMonitorAgent.cpp`).

Мной реализованы следующие сценарии тестирования:

* **Позитивные тесты (Positive Testing):** * Успешное включение устройства при точном совпадении `rrel_time_on` и `rrel_day`.
* Корректная обработка одновременного срабатывания расписаний для нескольких устройств (проверка многопоточности).


* **Граничные и негативные тесты (Negative Testing):** * Игнорирование триггера, если совпадает время, но отличается день недели (`rrel_day`).
* Fail-safe поведение агента: предотвращение падения системы (Segfault) при загрузке поврежденного SCs-графа (например, расписание без указания времени включения).


* **Проверка консистентности:** Гарантия того, что после отработки агента устройство имеет строго один валидный статус, а старые дуги `nrel_status` корректно удалены из памяти.

## Как это работает (Workflow)

1. **Инициализация:** Утилита `sc-builder` транслирует SCs-модели (комнаты, устройства, расписания) в бинарную графовую память.
2. **Тик времени:** `ScheduleTickerAgent` создает в графе узел `[08:00]`.
3. **Реакция:** Ядро `sc-machine` уведомляет `DeviceScheduleMonitorAgent` о появлении нового времени.
4. **Вывод:** Агент обходит граф, находит лампу в спальне, у которой `rrel_time_on: [08:00]`.
5. **Действие:** Агент переводит лампу в `concept_device_on`.
